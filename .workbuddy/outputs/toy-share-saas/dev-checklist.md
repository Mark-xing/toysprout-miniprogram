## 附录 · MVP 范围建议（评审用）

### 必须（MVP 上线门槛）
1. **业务规则拍板**：B-01~B-10 全部确认（服务费/会员/信用分/成色/运费/责任/互评/物流/仲裁/合规），否则定价、支付、信用、仲裁模块无法开发。
2. **小程序闭环**（原型已覆盖，工程化优先）：登录授权 → 发布（图片上传/成色/适龄）→ 发现流 → 发起交换（意向卡+聊天）→ 订单状态机 → 互评 → 信用分展示 → 服务费/会员支付。
3. **新页面必须项**：实名/家长认证（C-27）、地址管理（C-26，互邮前置）、纠纷入口（C-24 至少提交版）、登录注册（C-19）。
4. **后端基座**：数据模型（C-14）+ 真实数据接入（A-15）+ 物流单号自填与查询 API（C-07 聚合版）+ 支付（C-06）+ 埋点（C-13 最小集）。
5. **双端一致性收口**：A-06 信用分时间线、A-08 状态机语义色统一后上线，避免双端口径分裂。

### 可砍（V1.1 或之后）
- **推荐算法（C-15）**：MVP 用「时间+信用+同城」排序即可，算法留后。
- **收藏/心愿单（C-23）、通知中心（C-22）**：MVP 可用订阅消息替代通知中心；收藏可降级为「先浏览+发起意向」。
- **Web 完整后台（C-12）**：MVP 用云开发控制台 + 简化审核后台。
- **SSR/SEO（C-11）、搜索 ES（C-16 升级）**：MVP 静态落地页 + 数据库检索。
- **社区/环保可视化（D-04）、同城运营（D-06）**：均属增长/品牌期。
- **官方种子玩具池（D-01）**：属重运营方案，MVP 先靠社群种子用户冷启动，看数据再投入。

### 双端 MVP 页面分工
- **小程序（主阵地，全闭环）**：登录/发布/发现/详情/发起交换/聊天/订单详情/评价/我的/会员 + 认证 + 地址 + 纠纷提交。
- **Web（MVP 仅决策管理）**：落地页（营销静态）+ 我的/订单管理/会员订阅（决策与支付辅助）；后台管理延后。

### 结论
- 原型设计质量已通过（21/25，P1 清零），**设计侧无阻断项**；进入开发的最大前置依赖是 **B 类 10 项业务规则拍板**（决定数据建模与风控边界）。
- 建议排期顺序：**业务评审（B）→ 数据模型+小程序 MVP 闭环（C-01/02/05/06/14 + C-Ⅳ 必须项）→ Web 管理端与埋点（C-09~13）→ 增长/远期（D + P2 项）**。
